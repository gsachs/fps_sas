# Residual code-review findings — Visual Fidelity plan (U1-U5)

A 7-reviewer pass (correctness, testing, maintainability, learnings, performance,
reliability, adversarial — in-process; no cross-model peer was available in this
sandbox) ran against the full U1-U5 diff. All P1s and reasonably-scoped P2s were
fixed and verified (see commit `4077271`). Two findings were accepted as residuals
rather than fixed, both from the adversarial lens.

## 1. Multi-tick frame batching can silently skip a genuine wall-hit decal

- **Severity:** P2 (adversarial reviewer)
- **File:** `src/render/frameEvents.js:30,47-53` (root cause: `src/sim/index.js`'s
  `tick()` accumulates every sim step's events into one flat array before
  returning; `src/sim/loop.js`'s fixed-step accumulator can run up to ~15 steps
  in one stalled render frame, per `maxFrameSeconds / dt = 0.25 / (1/60) ≈ 15`)
- **Mechanism:** `shooterIdsThatHit(events)` (`src/render/impacts.js`) marks a
  shooter as "landed a hit" if *any* `'hit'` event for that shooter appears
  anywhere in the frame's batched events array. If a stalled render frame
  batches multiple sim ticks, and the same shooter both misses a wall and lands
  a hit within that one batch, `frameEvents.js` skips the decal for the miss
  too — not just the impact spark's color (the pre-existing, purely cosmetic
  behavior `impacts.js` already has), but the decal itself, entirely.
- **Why not fixed now:** A correct fix needs each `'fire'` event correlated to
  its own outcome — either tagging it in the sim (crosses KTD2's session-settled
  decision to leave the sim raycast/event contract untouched) or a per-tick
  correlation heuristic in the render layer (fragile: events from different
  shooters/entities interleave within and across the batched ticks). The
  consequence is bounded and purely cosmetic — CONCEPTS.md's own Impact Decal
  definition: "never affect physics, sensing, or gameplay" — and requires a
  compound rare condition (a frame stall long enough to batch ticks, exactly
  coinciding with the same shooter having mixed outcomes in that window).
- **Suggested follow-up:** If this is worth closing, the least invasive fix is
  giving `'fire'` events their own resolved-outcome tag at push time in
  `src/sim/world.js` (still inside the sim, no cross-boundary change, but a
  deliberate widening of the event shape) rather than reconstructing it
  after the fact in the render layer.

## 2. Decal dedup search doesn't check decals mid-eviction-fade

- **Severity:** P3 / advisory (adversarial reviewer)
- **File:** `src/render/decals.js` — `findDedupIndex` only scans `active`, not
  `retiring`.
- **Mechanism:** A re-hit on a spot whose decal is currently fading out after
  a cap-pressure eviction spawns a new decal instead of refreshing the fading
  one, briefly overlapping two marks in the same spot.
- **Why not fixed now:** Self-correcting within `EVICTION_FADE_SECONDS` (0.25s)
  — the fading decal disposes itself on schedule regardless. Advisory-tier per
  the reviewer's own classification; not worth the added dedup-scan complexity
  for a sub-second, purely visual overlap.
